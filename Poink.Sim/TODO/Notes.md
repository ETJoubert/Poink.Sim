Recommended starting configuration (Build Brain panel)
Encoders: Bar Window (Normalized) + Volume Profile (Normalized, lookback 50) — Trader State is appended automatically. Avoid the Raw normalization for anything that will run live: a network trained on literal price levels won't generalize to next month's price levels, let alone another symbol. Raw is a debugging view, not a training input.
Architecture: Your new CNN (kernel 3–5, channels like 16/32) over the bar window is the right main candidate — translation-invariant pattern detection over a 20-bar window is exactly what Conv1d is for. Keep MLP (64, 32, 16) as the control baseline; every experiment should beat it before it earns more complexity. Leave LSTM aside for now — recurrent nets under high-variance REINFORCE gradients are the hardest of the three to make converge.
Directions: All four, direction-only — no action-output heads yet. A 4-way categorical is already hard for REINFORCE credit assignment; adding Volume/SL/TP heads multiplies the joint action space before the direction signal exists. Add heads in a later phase, on top of a brain that already trades directionally better than baseline.
Risk caveat for later: direction-only means the hardcoded CapitalFraction = 0.5 at ComposedPolicyBrain.cs:35 and no stop-loss at all. Fine in the sim; not acceptable live. Before live use, either train the SL/TP heads or make the fallback fraction/SL configurable per brain.


3. Training-machinery upgrades, in order of value

Batch updates: accumulate 8–16 episodes per optimizer.step() instead of one. This is the single cheapest variance reduction available and fits your existing "one optimizer per run" design. One consideration: log-prob tensors currently keep their autograd graphs alive across the batch — for these small nets that's fine, but if memory bites, store encoded features per step and re-forward in one batch instead (which also unlocks PPO later).
Validation loop — the big one. Nothing today distinguishes learning from memorizing. Add to RlTrainingService: every N episodes, run a handful of evaluation episodes on a held-out date range (later than the training range, never sampled by RandomEpisodeWindow), with greedy action selection (argmax, no sampling) and no weight update. Track validation reward/equity separately in the Live tab, and treat "best validation score" as the snapshot worth saving — your snapshot-per-save history in IBrainRepository already supports keeping several and picking the winner.
Later, as a new IRlTrainingStrategy: actor-critic (a value head as learned baseline) and then PPO. Your coach abstraction was built for exactly this — new class plus one DI registration — but it's wasted effort until items 1–4 are in and a brain reliably beats the heuristic baselines.

4. Training strategy (phased campaign)
Phase 0 — baselines. Run RandomBrain and MomentumThresholdBrain over your validation windows and record equity/drawdown. These numbers are the bar; a trained brain that doesn't clear them on validation data is noise.
Phase 1 — pipeline smoke test, with one warning. DummyTickGenerator is a random walk, which by construction contains no learnable signal — the optimal policy on it is "never trade." It's fine for verifying the loop runs, but prolonged training on it actively teaches Hold. Worth adding a synthetic generator with a planted pattern (e.g. alternating trend/mean-revert regimes): if the brain can't extract a known edge from clean synthetic data, no amount of historic training will help, and you find that out in minutes instead of days.
Phase 2 — historic training. One symbol, training range = older ~80% of your collected ticks. Reward policy: start with EquityDriftRewardPolicy — it's unshaped and can't be gamed; shaped policies (TradingRules, MarketStructure) invite reward hacking, so introduce them only to correct an observed pathology (e.g. churn). Suggested knobs: 200–400 decision bars/episode, learning rate 1e-3 dropping to 3e-4 once reward trends, thousands of episodes, batched updates per upgrade #3.
Phase 3 — risk-adjusted fine-tune. Once directionally profitable on validation, switch to DifferentialSharpeRewardPolicy for a shorter run — for a live trader you want risk-adjusted return, not raw drift. Optionally add the Volume/SL/TP heads here.
Phase 4 — out-of-sample verdict. Best-validation snapshot into SimulationEngine against the newest, never-touched data slice. Compare equity curve, max drawdown, profit factor, and trade count against the Phase 0 baselines. Only a brain that wins here graduates.
Phase 5 — live path. This is currently missing: the cTrader robot only writes ticks to Postgres. The pragmatic bridge is to keep inference in Poink.Sim (it already owns TorchSharp, the encoders, and saved brains) and expose a tiny local decision endpoint the robot calls per bar — rather than porting the whole encoder/TorchSharp stack into the cAlgo sandbox. Start with the robot logging decisions without placing orders (paper mode) so live-fed decisions can be compared against the sim before real money moves.
